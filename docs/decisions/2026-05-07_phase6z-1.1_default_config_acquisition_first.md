## 1. Thesis 再平衡

### 1.1 衝突點

6z-1D force-modal 套用了 stroke-order 既有 memory **`feedback_d_c_strict_default`**「強紀律弱預設」 — 「force user verify, no silent defaults」。但這條 memory 來自 ops 場景（NIC 名稱錯=斷網 / schema 版本不對=資料壞）。

User 6z-1.1 反饋揭示了 stroke-order phase 6z 是 **acquisition-first UX target**，跟 ops 不同維度：

| 維度 | Ops (e.g. U5M60 NIC) | UX acquisition (Phase 6z) |
|---|---|---|
| 錯預設成本 | 斷網 / 資料壞 | 視覺不符使用者預期 |
| 修正成本 | 高（半夜跑機房）| 低（按一下換）|
| First-paint 成本 | 不重要（沒 user 競爭）| 致命（10 秒沒看到結果 = lost user）|
| 推薦預設策略 | 強紀律弱預設 | **預設要 senior、不要 absent** |

### 1.2 結論

**強紀律弱預設**（D-C）跟 **acquisition-first 預設**不衝突，是**不同 domain 的不同策略**。誤把 ops pattern 套進 UX = **過度套用通則 ignore 場景特殊性**。

對位 personal-playbook §0.4「重新框架問題 > 答問題」：應問「**這個 domain 的錯預設代價是什麼**」，而非「**所有預設都該 absent 嗎**」。

## 2. 變更清單

### 2.1 `zentangle.js`

新增：
```js
const DEFAULT_CONFIG = {
  char: "心",
  mode: "hollow",      // 空心填充
  tileSize: "standard", // 標準磚 (9 cm)
};
```

`boot()` 改：
```js
// 6z-1: applyConfig(restored) || openModal()
// 6z-1.1: applyConfig(restored || DEFAULT_CONFIG) + render — no first-paint block
applyConfig(readConfig() || DEFAULT_CONFIG);
renderOutline().catch(...);
```

`openModal()` 改：modal 開啟時 **pre-fill 當前 config**（user 是「修改」非「重新填」）。

`wireForceModal()` 改：移除 ESC + 背景 click block，改為 dismiss 後保留現有 config。

### 2.2 `index.html`

modal 文案：
- 標題 「開新紙磚」 → 「紙磚設定」
- 說明 「請選擇 3 項必填參數（無預設值）」 → 「修改紙磚參數 ... 初始已套用預設『心』+ 空心填充 + 標準磚」
- 底部 「⚠ 刻意無預設值 + 不可 ESC dismiss」 → 「💡 6z-1.1 thesis 再平衡：first-paint friction > 嚴格輸入紀律的 acquisition cost」

### 2.3 保留（未動）

- localStorage schema versioning（`CONFIG_SCHEMA_VERSION = 1`）
- `clearConfig()` + 重新設定紙磚 button → user 主動點仍可清空 + 重開 modal
- Confirm button 仍 require all 3 valid（即使有預設，user 修改後也要驗證）
- ACTIONS dispatch table + 鍵盤滑鼠 listener — 不受影響

## 4. P7-COMPLETION

- **任務**：移除 force-modal 對 first-paint 的硬性 block，改套合理預設
- **方案**：`DEFAULT_CONFIG` + `applyConfig(readConfig() || DEFAULT_CONFIG)` + modal 改非阻擋（ESC / 背景 click 可 dismiss + pre-fill）
- **改動**：3 files, ~30 lines diff
- **影響分析**：
  - boot 流程 1 處 if/else 變平鋪 → 簡化
  - modal lifecycle 從「強制阻擋」 → 「user-initiated」 → reset button 仍是入口
  - 既有 schema versioning + ACTIONS dispatch 完全不受影響
  - 33 tests 全 pass，無 regression
- **三問自審**：
  - 方案正確：是。Acquisition-first thesis 一致；保留 schema versioning 為將來預留
  - 影響全面：是。只改 boot + modal lifecycle，無 cross-cutting
  - 回歸風險：低。15 Node + 18 pytest 全 pass；改動範圍小於 50 行
- **剩餘風險**：
  1. **未來其他 domain 同樣需要這條決策** — 例：mandala mode 是否也該預設化？目前 mandala 已有 default 字，但 audit 未做
  2. **「預設要 senior」 標準** — 「心」 / 標準磚 / 空心填充 是 user 親自決的；其他 phase 預設值該 ask user，不該 silent decide

## 5. 經驗萃取（save 進 memory）

新 memory candidate（已 save）：

> **「強紀律弱預設」 vs 「acquisition-first 預設」 是 domain-specific 而非 universal**
>
> Ops 場景錯預設代價高（斷網 / 資料壞）→ force verify 合理。
> UX acquisition 場景錯預設代價低 + first-paint friction 致命 → 預設要 senior、不要 absent。
> 套既有 memory `feedback_d_c_strict_default` 進 UX 是過度套用通則。
>
> 對位 personal-playbook §0.4 重新框架：「**這個 domain 的錯預設代價是什麼？**」 才是該問的問題。
