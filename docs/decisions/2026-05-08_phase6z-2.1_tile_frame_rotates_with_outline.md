## 1. Bug Root Cause

### 6z-2 原實作 pipeline

```
applyRotation(deg)
  drawTileBackground()     ← axis-aligned (原 0°) 畫邊框 + 4 dot
  renderOutline()
    fetch outline
    mapContourToTile(...)  ← 計算 tile-local px
    rotateContours(...)    ← 只旋轉 outline polylines
    drawOutline(rotated)   ← 畫旋轉後的字
```

**結果**：邊框 + 4 dot **永遠 axis-aligned**；只有 outline 旋轉 → 視覺像「字在旋轉、紙磚不動」 = 違反 metaphor。

### 物理對應

「轉動紙磚」是把紙磚（含上面所有東西）一起翻 — 邊框、4 角點、字應該作為**整個 unit** 旋轉。Canvas 上的對應 = 整個 tile rendering 在同一個 ctx transform 下進行。

---

## 2. 修法：ctx transform 取代 polyline pre-rotation

### 2.1 新 helpers

```js
function clearCanvas() {
  // axis-aligned 清空 + 白底（一定 cover 整個 canvas，即使旋轉後）
}

function drawTileFrame() {
  // 邊框 + 4 角點（不含 clear；在 ctx transform 內呼叫）
}

function withTileRotation(fn) {
  if (_rotationDegrees === 0) { fn(); return; }
  ctx.save();
  ctx.translate(cx, cy);
  ctx.rotate(degToRad(_rotationDegrees));
  ctx.translate(-cx, -cy);
  try { fn(); } finally { ctx.restore(); }
}

function redrawAll() {
  clearCanvas();
  withTileRotation(() => {
    drawTileFrame();
    if (_cachedContours) drawOutline(mapContourToTile(_cachedContours, ...));
  });
}
```

### 2.2 旋轉一致性保證

`withTileRotation` 包住 `drawTileFrame` + `drawOutline` 兩個 → 同一 ctx transform 下 → 邊框 + dot + outline **數學上同步旋轉**，視覺一致。

### 2.3 為何 `clearCanvas` 在 transform 之前

旋轉後的 `clearRect(0,0,ts,ts)` 只清旋轉框內的區域；canvas 像素是 axis-aligned 的，所以清空必須在 axis-aligned 空間做（先 clear → 再 transform → 再畫）。否則切換 tile size / 大幅度旋轉時會殘留舊像素。

## 3. 順便修：6z-2 R1「Slider drag fetch race」 風險

6z-2 的 risk register R1 記錄：
> Slider drag 每次 input 觸發 renderOutline (含 fetch)；fetch 已 cache 同 char/source，但若 source 切換+slider 同時動可能 race。

6z-2.1 同時解決：

**新增** `_cachedContours` module state — 最後一次 fetch 成功的 polylines。
- `renderOutline()`: fetch → set cache → `redrawAll()`
- `applyRotation()`: 不 fetch，只 `redrawAll()`（用 cache）
- `tileSize change`: 不 fetch，只 resize + `redrawAll()`
- `char/source change`: 清 cache + `renderOutline()`（重 fetch）

**結果**：slider drag 100ms 拖 60 次 → 0 次 server hit、0 race risk、UI 即時跟動。

## 6. P7-COMPLETION

- **任務**：修旋轉視覺 bug — 紙磚 frame 應與 outline 共同旋轉
- **方案**：ctx transform (`save/translate/rotate/translate/restore`) 包住整個 tile rendering，取代 polyline pre-rotation；同時加 `_cachedContours` 解 slider drag fetch race
- **改動**：3 files (zentangle.js + pyproject.toml + 1 new doc)，~+90 / -60 lines
- **影響分析**：
  - `rotateContours` 純 helper 仍 export，將來 Pseudo-3D state-aware 操作 / SVG 匯出仍可用
  - 25 既有 Node test 全 pass（純 helper unchanged）
  - Backend pytest 18 pass、HTML smoke 10/10 → no regression
  - render pipeline 原 dual-call (`drawTileBackground + renderOutline`) → 統一 `redrawAll`，code path 更短
- **三問自審**：
  - 方案正確：是。Canvas ctx transform 是「整個 tile 旋轉」 的對應抽象；polyline pre-rotation 是子集
  - 影響全面：是。grep `drawTileBackground` 全 6 處都走 alias→redrawAll；無 dangling axis-aligned draw
  - 回歸風險：低。Pure helpers + Node test 100% cover；零 backend 改動
- **剩餘風險**：
  1. **Slider step=1 拖很大幅 drag** — 每 input 都觸發 redrawAll（mapContourToTile + drawOutline），仍可能 jank 在 學徒磚 900px 解析度。如真感慢，未來可加 requestAnimationFrame throttle，但 6z-2.1 接受此 trade-off
  2. **boot 流程 redrawAll 跑 2 次** — `boot()` 先 `drawTileBackground()` (= redrawAll 空磚) → `renderOutline()` 內又 `redrawAll()` 一次 → fetch 後再 `redrawAll()` 一次。共 3 次清+畫，但每次都很便宜（< 10ms）
  3. **若 user 機器無 moe_kaishu 字體** — fetch 503，`_cachedContours` 仍 null，redrawAll 只會畫空磚（旋轉但無字）。這是降級行為，符合 acquisition-friendly degradation
  4. **3-strike pattern 落實**：6z-2 ship → user E2E → 找到 visual bug → 6z-2.1 patch。今天第二次「ship 後 user catch visual bug」 (前次是 6z-1.2 force-modal)。Visual verify 仍是真完成度 gate

## 7. 經驗萃取（candidate for memory）

> **Canvas 整體旋轉用 ctx transform，不要對 primitive 個別 pre-rotate**
>
> 對於「整體變換」 視覺需求，ctx 變換 (translate/rotate/scale) 是統一抽象 — frame、outline、（將來的）filling、shadows 都在同一 transform 下保持一致。Pre-rotating polylines (e.g. via `rotateContours`) 是子集，僅該用於需要「**rotated state 真實存進 schema**」的場景（SVG export, .md serialization, snapshot）。
>
> **驗法**：當 visual element 群組旋轉時，問「**這群是不是該作為 unit 一起轉**？」 是 → ctx transform 包住整段 draw；否 → primitive pre-rotation 才合理。

候選新 memory，待 6z-3+ 出現相同需求時升格。
