## 一、5dp：抄經預覽 502 修復（0.14.193、msg 16）——sync def＋loader 記憶化

線上抄經「產生預覽」回 HTTP 502（等待過長、無反應）。本機量測一頁心經
（260 字位）純字形載入 ~十幾秒。兩個複合根因，各對一條鐵則：

① **async def 內跑重活凍住 event loop**（§9/5ck 再驗）：sutra_post／
sutra_get／sutra_pdf_endpoint 皆 async def、內跑十幾秒同步字形載入＋SVG
渲染，凍住 Render 單 worker 的唯一 event loop → 健康檢查/其他請求無法回應
→ 逾時 502。三端點改 sync def（FastAPI 自動走 threadpool、不凍 loop）。

② **per-位置 char_loader 無去重**：render_sutra_page 對每個字位呼叫
char_loader(ch)（一頁 260 位、117 唯一），而 _load 不快取。加
`_memoize_char_loader`（per-request dict cache）「每唯一字只載一次」：
預覽 ~15s → 2~3s。記憶化前後逐位元相同輸出（渲染器唯讀 Character）。

→ PRINCIPLES §19。

## 二、5dq：週期表只留形狀＋字源工廠快取（0.14.194、msg 17）

使用者：依範例改元素週期表排列。原 preset 會多輸出一頁「平鋪方格」的字，
週期表本身即完整排列 → index.html 抄經版面加 `tableOnly`（key==
periodic_table 且 ready），只出週期表頁。

此改暴露一個更深的效能舊帳：週期表 118 罕見字光載入 ~31s → 又會 502。
Profile 出根因比 5dp §19.2 **更上一層**：`_load` 每次都
`make_source(source)` 建**全新** AutoSource（含全新 MMHSource 重解 9500 行
~20s＋全新 MoeKaishuSource 重讀 CFF ~9s），把各字源的 per-instance 快取
整個丟掉重建。修法：make_source 加 `_SOURCE_CACHE`（同名字源 process 內
只建一次、跨請求重用，呼應既有 get_kaishu_source singleton 意圖）。
31s → ~3s。

配套：加了快取就要能失效——AutoSource 內含**可變**的 UserDictSource，
故 user_dict 的新增/刪除/匯入三端點寫入成功後呼叫 `reset_source_cache()`
（回歸測 test_api_user_dict_override_visible_in_notebook 正是抓這個）。

→ PRINCIPLES §20（昂貴工廠跨呼叫快取，但可變資源寫入端須主動失效；
cache-and-invalidate 成對）。

## 五、5dt：逐字手寫（0.14.197、msg 20）——互動新功能

使用者：抄經產生預覽後，點描紅格子的字→彈窗手寫→送出/上一字/下一字自動
送出→寫的字呈現在預覽描紅格→存本機、可分段、可下載/匯入。

QODA 定案：全域覆蓋（user-dict）＋新做專用逐字彈窗（兩者皆使用者選推薦）。
關鍵發現——**八成後端已存在**：罕用字管理的手寫畫布、POST /api/user-dict、
匯出/匯入、AutoSource「user_dict 最優先」使手寫自動覆蓋描紅。新做只是接
起來：
- 後端：render_sutra_page 加 `emit_cellmap`（預設 False，僅預覽端點開），
  為每個字格發透明 rect 帶 data-char/data-pos（fill="transparent" 才收
  得到點擊）；SVG 下載/PDF 不受汙染。
- 前端：新 modal「逐字手寫」——米字格畫布＋淡色範字、上/下字/略過/送出，
  沿用畫布捕捉與 user-dict 端點；點預覽格→開彈窗→送出→關閉時重繪預覽。

Playwright 端到端驗證（心經 260 clickable 格；點第一格→彈窗開於「觀
第 1/260」→注入筆畫送出→user-dict 收到→下一字自動送出移到「自」）。

→ PRINCIPLES §23（互動地基靠伺服器發 data-* 標記、前端只掛事件；預覽互動
層用旗標與下載/PDF 分流；新功能優先重用既有存儲）。

## 七、5dv：手寫可見修復＋彈窗重排＋週期表微調（0.14.199、msg 22）

三件回饋：

① **核心 bug：逐字手寫送出後格子變空白**。根因：手寫是 centerline
（raw_track、無 outline），render_sutra_page 把它落入「隸/篆骨架層」，
而該層 opacity 被刻意調成 0.03（§5cb，隸/篆 centerline 不完美、故意
near-invisible）→ 手寫幾乎不可見＝看似空白。修法：依 data_source 分流——
手寫（data_source 以 "user" 開頭）改走新的可見層 `sutra-trace-user`
（opacity 0.9），隸/篆保留 0.03。

② 逐字彈窗按鈕重排：復原/清空疊畫布左上角（overlay）、上/下字/略過移到
畫布右側直欄、彈窗加寬 520→600px 讓右欄容得下。

③ 元素週期表版面：新增 _ROW_OFFSET=3、_COL_OFFSET=1——整體下移 3 列、
右移 1 欄，18 欄週期表在 20 欄格中左右各留 1 空欄（水平置中）。

→ PRINCIPLES §25（渲染層視覺參數是為某來源調的，新來源同形不同義要依
data_source 分流；加功能要端到端驗到「使用者實際看到的那一格」——5dt 只
驗到「有沒有存進 user-dict」，漏驗「存了之後在預覽長什麼樣」）。

## 弧終帳（5dp→5dv）

版本 0.14.193 → 0.14.199（七輪）；README badge tests 本機 1691 → 1700、
node 257 不變。全弧零新增依賴（opencc/FastAPI/numpy 皆既有）。

**這一弧的主線**是「深化抄經模式」，但真正貫穿的是三條方法論，且都在
本弧被正反例印證：

1. **重用勝於自造**——5dt 逐字手寫八成掛在既有 user-dict＋畫布上；5du
   週期表重用 render_sutra_page。反例：5ds 一度自繪米字格，5du 才修正。
   （§23.3、§24）
2. **視覺需求先出 mockup 再實作**——週期表三迭代都先給圖/截圖確認版面與
   取捨（標題去留、置中偏移），省下猜錯重做。（§22.2）
3. **端到端驗到使用者看到的那一格**——5dt 只驗資料寫入、漏了預覽呈現，
   5dv 才抓到手寫被 0.03 opacity 吃掉。加功能的驗收邊界要拉到「畫面」，
   不是「資料」。（§25）

穩定性上，兩次 502（5dp async-def／loader 去重、5dq 字源工廠快取）把
「重端點在 Render 單 worker 上的成本模型」補完：呼叫次數 × 單次成本 ×
工廠重建成本，三軸都要顧，且快取要配失效。
