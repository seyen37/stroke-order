# 評估建議書：方寸 FANGCUN 參數化字型 × stroke_order 改善路線

日期：2026-08-11｜評估對象：[方寸 FANGCUN](https://fangcuntw.vercel.app/)（參數化繁體中文字型工作室）
本專案：stroke_order（中文字元 → 向量筆跡，寫字機器人／雷雕工具，v0.14.263）

---

## 0. 摘要（一段話版）

FANGCUN 的核心命題——「存骨架不存輪廓，一個參數改 13,000 字」——與 stroke_order 的
DNA **高度同源**：你的專案本來就以「每筆一條路徑」的骨架資料（zh-stroke-data、
KanjiVG、手寫軌跡）為第一公民，FANGCUN 視為獨家的 per-stroke path，正是你已有的地基。
差別在方向相反：FANGCUN 從骨架**向上**合成印刷字型（OTF），stroke_order 從骨架**向下**
驅動實體輸出（筆跡、G-code、雷雕）。因此**不建議正面做字型工作室**，但有四項技術
非常值得借鏡，其中「參數化字模引擎」還能順手根治你現有的「字型部署相依」痛點
（noto_hei 缺字型 → 503／測試 skip 那條）。

## 1. FANGCUN 架構解讀

### 1.1 它怎麼做到「一個參數改 13,000 字」

三層式架構：

1. **骨架層（skeleton）**：每個字存的是筆畫骨架（中心線＋筆畫類型），不是輪廓。
   資料源是 [GlyphWiki 字形維基](https://zht.glyphwiki.org/)——KAGE 系統的自由資料
   （每字＝筆畫清單，每筆＝類型＋控制點；部件可引用其他字形＋包圍盒變換）。
2. **筆畫渲染層（stroke rendering）**：把骨架「長肉」成輪廓的規則引擎——同一條骨架，
   依參數（字重、對比、圓角、出鋒）渲染成不同粗細形狀的筆畫外形。
3. **結構規則層（structure）**：全字層級的幾何變換——字面率、中宮等比例參數。

因為 13,000 字共用同一套渲染規則，改參數＝改規則＝全部字一起變。這是把
「設計 13,000 個輪廓」壓縮成「設計一套規則＋13,000 份骨架資料」的槓桿。

### 1.2 公開的參數軸與匯出鏈

- 參數軸：字重（weight）、對比（contrast）、圓角（rounding）、字面率、中宮、出鋒、
  尺寸與間距；五個預設風格（明體／圓體／楷書／黑體／基本）。
- 匯出：OTF（全量或子集）、SVG（明列 Illustrator／雷切／CNC 用途）、PNG、變數字型。
- 技術棧線索：opentype.js（MIT）＋ polygon-clipping（MIT），純前端（Vercel 靜態站）。
- 品保：迴歸測試（跨版本追字形變動）＋幾何驗證（自交、NaN、包圍盒越界）。

### 1.3 授權結構

- 字形資料：GlyphWiki——「登記其上的資料、文件與產生的字型，使用皆為自由無償」。
- 程式碼：MPL-2.0（商標除外）。**注意：概念與架構可借鏡，程式碼不可直接抄**
  （MPL-2.0 是 file-level copyleft；你的專案是 MIT，混入 MPL 檔案會帶入額外義務）。
- 匯出字型：使用者保有權利（隨 GlyphWiki 自由授權）。

### 1.4 技術評估：強項與限制

**強項**：架構槓桿真實存在（骨架×規則＝全字聯動）；匯出鏈完整到「可安裝的 OTF」，
把玩具做成了工具；SVG per-stroke 路徑直接對接雷切／CNC（與你的用戶重疊）；
幾何驗證＋迴歸測試的品保意識到位。

**限制與風險**：(a) 參數化合成的字形品質天花板——KAGE 骨架是印刷體導向的簡化描述，
極端參數下細節（起收筆、避讓、重心）不如人工修字，商用內文字型仍打不過傳統鑄字；
(b) GlyphWiki 資料品質不均（社群編輯，字與字之間骨架精度有落差）；(c) 對比、出鋒這類
書法感參數在複雜字（30+ 筆）容易糊；(d) 無明確商業模式（免費），持續性未知。
這些限制對它是問題，**對你反而是機會**——你的輸出場景（雷雕、鏤空、筆跡）對字形
細節的容忍度遠高於印刷內文。

## 2. 與 stroke_order 的 DNA 對照

| 面向 | FANGCUN | stroke_order | 判讀 |
|---|---|---|---|
| 核心資料 | KAGE 骨架（GlyphWiki） | 骨架（zh-stroke-data/KanjiVG/手寫軌跡）＋輪廓（CNS/教育部/Noto/崇羲） | **同源**——你雙軌並存，比它多輪廓軌 |
| per-stroke path | 主打「只有本系統有」 | 本來就是第一公民（IR 的 Stroke 即單筆） | 它的獨家＝你的日常 |
| 方向 | 骨架→合成印刷字型（向上） | 骨架→實體輸出 筆跡/G-code/雷雕（向下） | 互補不競爭 |
| 參數化 | 骨架「長肉」規則引擎（7 軸） | 尚無——字模靠現成字型檔輪廓 | **這是它有你沒有的一塊** |
| 匯出 | OTF/SVG/PNG/變數字型 | SVG/G-code/DXF/PDF/PNG/GIF/ODP | 你多機具格式，它多 OTF |
| 缺字處理 | GlyphWiki 覆蓋廣（含罕字） | CNS 全字庫＋篆體部件合成（§53 誠實放棄曲線） | 它的資料源可補你的縫 |
| 品保 | 幾何驗證＋迴歸測試 | 1855 測試＋守門鎖不變式（§66） | 同文化，可互相印證 |

**關鍵洞察**：你已擁有 FANGCUN 最貴的資產（骨架資料×多來源），缺的只是它的第二層
——「骨架長肉的參數化渲染規則」。補上這一層，你的骨架就能在**沒有任何字型檔**的
情況下自產字模。

## 3. 改善建議（QODA 選項，各自獨立、可分批 sign-off）

### R1★★★ 參數化字模引擎：骨架「長肉」自產字模（推薦首發）

**Question**：stroke_order 的鏤空／立體字／卡片字模目前依賴字型檔輪廓
（noto_hei 等），造成「字型是部署相依」的長尾（缺字型 → 503、測試 skip、
開發機要手動放字型、Render 要 fetch 腳本）。能否讓骨架自己長出字模？

**方案**：新增 `exporters/skeleton_glyph.py`（或 sources 一員）：取既有 IR 骨架
（zh-stroke-data 中心線），實作最小可用的「長肉」渲染——沿骨架掃描等寬/變寬筆形
＋端點帽（圓/方）＋轉角處理，polygon union 成字身輪廓。第一版只做 2–3 個參數
（字重、圓角、字面率），就足以供鏤空/popup/卡片當字模。

**價值**：(a) 字模不再必需字型檔——缺 Noto 時誠實降級到骨架字模而非 503，根治
部署相依長尾；(b) 全部 13,000+ 字（zh-stroke-data 覆蓋範圍）自動可用；(c) 參數滑桿
＝新的玩法（粗體鏤空、細體刻字），直接複用你現成的滑桿＋即時預覽 UI 慣例。
**工作量**：中（幾何核心 2–3 個檔；Python 端有 shapely/既有 polygon 工具可用）。
**風險**：長肉品質第一版必不如真字型（起收筆呆板）——但你的雷雕/鏤空場景容忍度高，
且可定位為「降級階梯的一階」而非替代 Noto。
**明確不做**：不追 FANGCUN 的 7 軸全套（對比/出鋒/中宮留待有需求再說）。

### R2★★ GlyphWiki（KAGE）作為新字形來源

**Question**：罕字/異體字缺字時（篆體部件合成那條線已見過 60 缺字），要不要多一個
自由資料源？

**方案**：新增 `sources/glyphwiki.py`：抓 KAGE 資料（單字 API 或 dump），解析筆畫
描述為 IR 骨架。與 R1 組合後 = 罕字也能長出字模。
**價值**：缺字覆蓋率大增（GlyphWiki 含大量 Ext B-G、異體、和製漢字）；資料自由無償、
授權乾淨（納入現有 licenses/ 治理即可）。
**工作量**：中（KAGE 格式解析＋部件引用展開；有社群文件可依）。
**風險**：資料品質不均——沿用你 §8 降級誠實原則，來源優先序排在 zh-stroke-data 之後。

### R3★★ 手寫轉字型：user_dict 軌跡 → OTF（差異化殺手鐧）

**Question**：FANGCUN 證明了「瀏覽器就能出 OTF」（opentype.js）。你有它沒有的東西
——使用者親手寫的軌跡（手寫練習/user_dict 已存 EM 2048 座標折線）。要不要讓使用者
把**自己的手寫**變成可安裝的字型？

**方案**：手寫軌跡（骨架）→ R1 的長肉引擎 → 輪廓 → fontTools 組 OTF（Python 端，
你已有 fonttools 相依）。先做「寫過的字＋常用字集」子集字型。
**價值**：「寫字機器人工具」→「你的手寫變成字型」是情感價值極高的獨家功能，
FANGCUN 做不到（它沒有使用者手寫資料）；與 R1 共用同一顆長肉引擎（一魚兩吃）。
**工作量**：中大（OTF 組裝、字符映射、度量）。**建議排 R1 之後**，引擎先熟。

### R4★ 參數即時預覽的 UX 借鏡（輕）

FANGCUN「拉一個參數、整頁字一起動」的即時感是其最強的第一印象。你的滑桿 UI 已有
此慣例（popup 的字高/roof/tread），R1 落地時把「字模參數→預覽即時連動」做足即可，
不需獨立立項。**工作量**：小（隨 R1 附帶）。

### 明確不建議：完整字型工作室

與 FANGCUN 正面競爭（7 軸、變數字型、全字集 OTF 工作室）不做——它已免費開源、
先行且聚焦；你的護城河在實體輸出鏈（G-code/雷雕/機構如立體字）與手寫資料，
資源該壓在 R1/R3 這種「它做不到、你順手」的位置。

## 4. 優先序與路線圖（建議）

| 順位 | 項目 | 價值 | 工作量 | 相依 |
|---|---|---|---|---|
| 1 | R1 參數化字模引擎（字重/圓角/字面率） | 高（根治字型相依＋新玩法） | 中 | 無 |
| 2 | R3 手寫轉 OTF | 高（獨家差異化） | 中大 | R1 引擎 |

分批進行、各自守 QODA：R1 落地驗證品質可接受後，再決定 R3/R2 是否啟動。

## 5. 授權與合規注意

1. **MPL-2.0 程式碼不可複製貼上**進你的 MIT 專案（file-level copyleft）；架構概念、
   參數軸設計、演算法思路可自由借鏡。自己實作即可（你的幾何工具鏈本就齊全）。
2. **GlyphWiki 資料自由無償**（含產出字型）——若做 R2，比照本輪 licenses/ 治理慣例，
   在 `LICENSE` 第三方資料源 A 段＋`licenses/` 加對應條目。
3. R3 產出的使用者手寫字型，著作權歸使用者（其手寫為其創作）——匯出時附一行
   說明即可，別替使用者宣告授權。

## 6. 結論與下一步

FANGCUN 驗證了「骨架×參數規則」路線在繁中 13,000 字尺度上可行，而 stroke_order
握有同源且更豐富的骨架資產。最划算的一步是 **R1 參數化字模引擎**：工作量中等、
直接根治現有部署痛點、為 R3（手寫轉字型）鋪路，且完全避開與 FANGCUN 的正面競爭。

**等你 sign-off**：選 R1 就緒後我出細部技術規格（QODA 步驟 1-2：模組邊界、
幾何演算法選型、測試不變式）再動工；也可以先只做 R1 的 spike（單字驗證長肉品質）
降風險。
