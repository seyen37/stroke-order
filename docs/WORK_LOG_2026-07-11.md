## 二之六、第六批（同日續）：5br 布章排字重疊修正

user 線上實測回報：80mm 布章放 4 個 22mm 字全部疊在一起。根因：
`_layout_text_positions` 直排邏輯把字心均勻撒在可用寬度，從未檢查
字心距是否小於字寬（4×22mm 案例字心距僅 12mm）。

修法：新增 `_fit_char_size()`（裝不下時自動縮字，上限
w/(n×1.08+0.3)）＋字心距下限 eff×1.08＋統一置中公式；layout 回傳
`(positions, 有效字大小)`，SVG／polylines（G-code/DXF）兩個消費端
同步用有效字大小繪製。空間充裕時位置與舊公式完全一致（回歸零差
異），擁擠時自動縮字排開。+4 tests（重疊場景／寬裕不變／單字／
弧排 clamp）。

附帶發現（未修）：布章 cut SVG 的字形 stroke-width 在 scale 變換
下縮小 118 倍，cairosvg 端渲染成隱形髮絲線（瀏覽器預覽正常）。
記入 followup。

## 二之二十一、第二十一批（同日續）：5cm importScripts 懸掛實錘

5cl 部署後複驗：伺服器一切正常（/vendor/status cached:true、
瀏覽器實測 fetch 10.3MB 965ms），前端依然永久「產生中…」。
Chrome MCP 實機解剖（8 組對照實驗，全在使用者的校網環境）：

| 實驗 | 結果 |
|---|---|
| 主執行緒 fetch /vendor/opencv.js | 965ms ✓ |
| 裸 worker 頂層 importScripts（絕對 URL） | 363ms ✓ |
| 引擎共存＋async handler＋絕對 URL importScripts | 3/3 ✓（最慢 2.3s） |
| 正式 worker 引擎內建相對路徑 importScripts | 3/3 永久懸掛 ✗ |
| blob worker 相對路徑 | 即刻 SyntaxError（基底無法解析） |
| jsDelivr importScripts（校網） | 靜默丟包 → 同步無限阻塞 ✗ |

修正三件：① OPENCV_CDN_URLS 同源位址以 location.origin 絕對化
② worker 載入改 fetch（15s chunk 逾時＋MB 進度回報）＋間接
eval ③ script tag 20s 逾時＋renderVia 90s 進度看門狗
（terminate → 主執行緒 → 伺服器，降級階梯復活）。

- 教訓一：**worker 的同步 importScripts 是三重黑箱**（不可逾時
  ／不可中斷／錯誤不可見）——載入路徑可能經防火牆時一律
  fetch＋eval
- 教訓二：**降級階梯每層都要有看門狗**——任一層懸掛（而非
  失敗）就會凍住整條階梯；「失敗會往下走」的假設只對「會
  回報失敗」的層成立
- 教訓三：**Chrome MCP 實機解剖是校網類問題的正解**——同一
  段程式在我的環境與使用者環境行為不同時，直接在使用者的
  瀏覽器裡做對照實驗，八組實驗把猜測空間收斂到單點

## 二之二十三、第二十三批（同日續）：5co eval 黑箱實錘、回 importScripts

5cm 部署後 Chrome 實機驗收：下載鏈痊癒（絕對 URL＋MB 進度
1→9 秒級），但「編譯（WASM 初始化）」永久卡死——10MB 間接
eval 在引擎情境 CPU 懸掛（probe 訊息都進不去）。追加八組
對照的詭異結論：同一字串 inline eval 216ms ✓、引擎內同一行
無限卡 ✗、**連把 self.eval 攔截包一層再轉呼叫都會讓它恢復**
——V8 大字串 eval 行為依呼叫情境而異，不可依賴。

工程決策（5co）：執行回全日 4/4 穩定的 importScripts(絕對
URL)，fetch 降級為「看門狗＋MB 進度＋快取暖身」——silent-drop
在 fetch 層就被逾時擋下換源，importScripts 讀暖快取不碰網路。
部署前以 blob worker 複製 5co 組合預驗：1268ms 全通。

- 教訓：**10MB 級大字串 eval 是行為不穩定的黑箱**；大型第三方
  腳本在 worker 一律 importScripts，fetch 當觀察窗
- 方法論沉澱：「壞掉的那層不修，改讓它永遠不會走到」——
  fetch 把所有網路不確定性吃掉後，importScripts 只剩純執行

## 二之二十四、第二十四批（同日續）：5cp 環境層病灶定案、體驗保底

5co 部署後最終驗收（含使用者無偵錯器人工原生測試）：opencv.js
在「正式執行管道」（URL worker importScripts／主執行緒 script
tag／worker eval）於這台受管理電腦一律懸掛；**同 bytes 在 blob
worker 4/4 成功（最快 420ms）**。定性：環境層病灶（疑端點防護
掃描大型腳本執行／code cache 寫入卡死），非專案邏輯錯、網頁端
不可修。

體驗保底三件：預設引擎改伺服器（5ch 輪廓向量化）、OpenCV 降
實驗性＋sessionStorage 失敗記憶（失敗即自動改伺服器並明講、
成功洗白）、看門狗 90s→30s。§8.3（改預設值先 grep 全測試）
第三度應驗——5cb 舊斷言釘 browser 預設，沙箱預跑抓到。

- 教訓一：**「同 bytes、不同執行管道、結果迥異」＝環境層嫌疑**，
  blob worker 是快速對照組
- 教訓二：環境層病灶的正解不是繞（每繞一層它換個地方卡——
  importScripts 卡、eval 卡、script tag 也卡），是把預設路徑
  換到不受影響的引擎＋失敗記憶
- 教訓三：**驗收要含「無儀器的人工原生測試」**——CDP 偵錯器
  本身就是一個會改變行為的變因
