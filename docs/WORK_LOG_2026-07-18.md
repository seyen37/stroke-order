# WORK_LOG 2026-07-18

## 5ea：抄經篆書 HTTP 500 修復——單一字形風格轉換失敗不再整頁 500（0.14.205）

### 症狀（使用者實測回報）

抄經模式選「篆書（崇羲）」風格，元素週期表頁：篆體字沒出現、狀態列
「失敗：HTTP 500」。

### 根因（沙箱注入實錘）

`500 = 應用層例外`（memory：Render 逾時是 502，這裡是 500）。篆書用真
崇羲篆體字型時，其 skeleton／thinning 抽取（`chongxi_seal.apply_seal_
outline_mode` → `cns_skeleton.outline_to_skeleton_tracks`，docstring 自警
「runs slow / OOMs on dense outlines」）在某些 dense／degenerate 字形上會拋
**非 HTTPException** 例外（週期表有 astral-plane 罕用元素字 𨧀𨭎… 等）。

而 server.py 每個 `_loader` 都是 `try: _load → _upgrade_to_seal → …
except HTTPException`——**只 catch HTTPException**。於是 seal skeleton 拋的
ValueError／MemoryError 等穿過無防護的 `_upgrade_to_seal` → loader 接不住 →
整頁 500、篆體全不出現（預覽停在舊的楷書畫面）。

沙箱無真篆體字型（GitHub release 403），改以 NotoSansTC 當替身 + 注入會拋
例外的 `_apply_seal_mode` 兩向實錘：舊版無防護 → **500**；加防護 → **200**。

### 修法：根部優雅降級（一改保護全部 loader）

server.py 有 10+ 個 loader 都是同一模式，逐一改不 DRY。改在**根部**——
`_upgrade_to_seal` 與同構的 `_upgrade_to_lishu`——把 mode 應用包進 try，
任何非 CharacterNotFound 例外一律**退回楷書基底字**（正合 `_upgrade_to_seal`
docstring「真篆體，或 vanilla 楷書」的設計）。單一字形失敗絕不讓整頁 500；
其餘字形照常出篆體／隸書。

判準（可入 PRINCIPLES）：**批次渲染裡，單一元素（字位）的可選增強失敗，
必須被侷限成該元素降級，不能讓整個批次（頁）失敗。** 增強函式應在自己內部
把例外收斂成「退回基底」，別依賴每個呼叫端的 loader 各自防護（會漏）。

### 驗證

- 回歸測試 +2（tests/test_styles.py）：注入會拋例外的 `_apply_seal_mode`／
  `_apply_lishu_mode`，斷言 `_upgrade_to_seal`／`_upgrade_to_lishu` 回傳基底
  字、不拋。
- 端點級注入（沙箱）：週期表 + 篆書 + 注入爆炸 → 舊版 500、新版 200。
- 全量 pytest 沙箱 **1723 passed / 0 failed**（1721→+2）。
- 0.14.204→0.14.205、badge tests 1714→1716（+2 離線）、node 257 不變、零
  新增依賴。

### 使用者影響 / 邊界

- 修後：抄經任何經文選篆書／隸書皆不再 500。**有收錄於篆體字型的字出篆體、
  未收錄或字形爆炸的字退回楷書**（維持既有警語「部分罕用字未收錄，無法呈現」）。
- 週期表因多為 astral-plane 罕用元素字、篆體覆蓋本就低，仍多顯楷書＝正常；
  一般經文（心經等）篆體覆蓋高、應正常出篆體。
- 未能在沙箱以「真篆體字型」重現確切崩字（403 抓不到字型）；以注入等價機制
  實錘機制並鎖回歸。待 Render 部署 + 家用機真字型複驗。

## 5ed：骨架平滑——Chaikin 削角平滑 Zhang-Suen 骨架（0.14.208）

下弧候選「骨架平滑」。QODA 使用者選「A：Chaikin 削角」。

### 背景

`cns_skeleton.outline_to_skeleton_tracks`（Zhang-Suen 細線化→trace→
simplify_step 抽點）輸出是**像素階梯**折線（staircase-jagged），只抽點無曲線
平滑。消費者：篆書（chongxi_seal）／隸書（moe_lishu）／宋體（moe_song）／
CNS 全字庫（cns_font，v1＋v2）——都是描紅骨架、故鋸齒。

### 做法（cns_skeleton.py 一處，全消費者受惠）

- 新增 `chaikin_smooth(points, iterations=2)`：Chaikin 削角——每個內部轉角
  換成相鄰段 1/4、3/4 兩點，**端點精確保留**（筆畫起訖不移）；每迭代約倍增
  點數、腰斬最尖轉角。`iterations<=0` 或 <3 點 → 原樣返回（安全 no-op）。
- `outline_to_skeleton_tracks` ＋ `_v2` 各加 `chaikin_iters=2` 參數，em 座標
  轉換後套用。預設開（2 迭代：階梯 90°→26.6°，讀來平滑又不過度圓化真轉角）；
  `chaikin_iters=0` 保留原鋸齒（opt-out）。

判準：平滑度以「最大轉角」度量、非「總轉角」——Chaikin 守恆總轉彎、把它
分散到更多更小的角，故**總和不變、最大轉角遞減**才是正確指標。

### 驗證

  （45°→26.6°）、增點、iters=0/負 passthrough、短/空路徑 no-op、
  outline_to_skeleton 平滑 opt-out（筆畫數不變、增點、不比原始更尖）、預設
  套用。既有 seal/lishu/song/cns 測試（斷言穩健下界：筆畫數≥、raw_track≥2、
  點數≥）Chaikin 預設開全綠。

## 5ee：抄經 PDF 手寫層真的可見——修 cairosvg 髮絲線隱形 bug（0.14.209）

下弧候選「抄經 PDF 併 user 手寫層」。QODA 使用者選「A：現況就好（取代式）」。

### 誠實更正（我先前講錯）

我原先回報「PDF 已含手寫（混和）」是**錯的**。實際只在 SVG／瀏覽器成立；
下載的**光柵化 PDF 裡手寫是隱形的**。查證後向使用者更正了此記錄。

### 根因（cairosvg 光柵化實錘）

骨架／手寫 `<polyline>` 畫在 `<g transform="…scale(EM→mm)…">` 內（EM 2048
→ 約 12mm，scale≈0.006）。線寬本靠 `vector-effect="non-scaling-stroke"`
在**瀏覽器**維持螢幕像素寬——但 **cairosvg 不支援 vector-effect**、忽略它，
於是 stroke-width 被內層 scale 縮成 ~0.005mm 髮絲線 → PDF 光柵化幾乎 0 墨、
手寫層等同隱形（`_ink` 增量 == 0，各門檻皆然）。

### 修法（sutra.py，一處機制）

- `_render_skeleton_glyph` 加 `stroke_width_mm` 參數：給值時每條 polyline 帶
  **顯式** `stroke-width = stroke_width_mm / scale`，讓內層 scale 還原後恰為
  目標 mm——**任何光柵器**（含 cairosvg）都吃。None 時保留舊 vector-effect
  形式（瀏覽器呼叫端不變）。
- `render_sutra_page` 呼叫點傳 `stroke_width_mm = char_size ×
  _SKELETON_TRACE_STROKE_RATIO`（0.12）；user 手寫層 `<g>` 同樣改用具體
  mm 線寬 `user_stroke_w = char_size × 0.12`（不再靠 vector-effect）。

判準（承 5ea 系列）：**跨渲染器的線寬絕不能只靠 `vector-effect`——瀏覽器
專屬、cairosvg／PDF 會忽略。凡輸出要進 PDF 的向量筆畫，須帶「經 scale 還原
後為實體 mm」的顯式 stroke-width。**

### 驗證

- 單元 +2（tests/test_sutra.py）：`test_5ee_skeleton_glyph_explicit_width_
  defeats_vector_effect`（給 mm→有 stroke-width、無 vector-effect；不給→保留
  vector-effect）、`test_5ee_user_handwriting_renders_in_cairosvg_raster`
  （cairosvg 實際光柵化，斷言含手寫頁墨量 > 空白頁）。既有 5bx 測試改名
  `test_5ee_skeleton_polylines_carry_explicit_stroke_width`、斷言由
  vector-effect 改為顯式 stroke-width（機制已換）。
- 光柵化墨量實測（cairosvg 1000×700，門檻 <250）：空白頁 76646 →含手寫
  76915，**增益 +269**；修前（vector-effect 髮絲線）各門檻增益皆為 0（隱形）。
- 全量沙箱 **1732 passed / 0 failed / 54 skipped**（5ed 1730 → +2）。
- 0.14.208→0.14.209、badge tests 1723→1725（+2 離線）、node 257 不變、零新增
  依賴。

### 使用者影響 / 邊界

- 修後：抄經頁**有加入手寫的字，本頁SVG／全部SVG／整本PDF 都真的出手寫**
  （取代式：手寫覆蓋範例骨架）；未寫的字照出範例骨架。
- 沙箱以 cairosvg 光柵化墨量正錘（+269 vs 0）；PDF 端點走同一
  `render_sutra_page`→cairosvg→PNG→Pillow 管線，故 PDF 亦得。待 Render 部署後

## 5ef：切割風格 registry 重構——立可切換 seam、行為逐位元保存（0.14.210）

下弧候選「切割風格 registry 重構（承 5dm）」。QODA 使用者選「A：純 registry
重構」（而非 B 順便做 envelope、或 C 暫緩）。

### 背景（承 5dm STENCIL_CUTTING_STYLES.md §4/§5）

5dm 把字模的「切割策略」與「筆形字型」歸納為兩條**正交軸**（文件 §7）：
筆形由 `zentangle.SOURCE_REGISTRY`（選字型）免費提供，引擎只需管**切割
策略**軸。該軸的定義參數＝`connect_depth`（連筋深度）。但切割參數當時**散
在** `stencil.py` 的函式引數（`bridge_width_mm`/`bridge_count`/`frame`…）與
模組常數（`_ESCAPE_AXES`/`near_wall`…），且程式裡**實際只有一種策略**——
全連派（`connect_depth=full`、殘腔 0）。文件 §5 即該重構的規格藍圖。

### QODA 取捨（為何選 A）

關鍵張力：**registry 只有 1 個 entry 本身＝過早抽象（YAGNI）**；但使用者
明確點名此弧、文件是刻意留的藍圖、第二風格（envelope）已設計好——這讓它
從「臆測」變「已規劃」。而 `envelope`（只斷外框、留深層 counter）對本引擎
其實不小（要依巢狀深度分類 counter），且嚴格說是**新功能非重構**，混進
「重構」會弄糊「行為不變」的驗證保證。故選 A：純 seam、行為保存，`envelope`
接在後面當獨立功能弧（符合「量測先於機制、最小範圍、重構與加功能分離」）。

### 做法（stencil.py＋server.py，最小 seam）

- **registry**：`stencil.py` 新增 `@dataclass(frozen=True) CuttingStyle(key,
  label, connect_depth)`＋`CUTTING_STYLES = {"physical": …full…}`＋
  `get_cutting_style(key)`（未知→KeyError）＋`DEFAULT_CUTTING_STYLE`。
  **最小欄位**：只承載真正**選擇程式路徑**的 `connect_depth`（＋UI/header
  用的 `label`）；§4 其餘參數目前在 carve 函式內恆為 full 值，待 envelope
  需要時再拉進（YAGNI：不加沒程式讀的 dead 欄位）。
- **`stencil_geometry`** 加 `style="physical"` 參數：解析 style →
  `stats["style"]` 記錄 → connect_depth dispatch（非 `full` 拋
  `NotImplementedError`，證明 dispatch 真讀 connect_depth、非死參數；留給
  envelope）→ 既有全連派路徑（stencil 鑿橋／cutout 連筋）**原封不動**。
- **`/api/stencil`** 加 `style` query（預設 physical）：仿 `source` 驗證，
  未知風格 → 422；傳入 `stencil_geometry`；回應加 `X-Stencil-Style` 標頭。
- **UI 不動**：1-選項下拉＝噪音；下拉連同 envelope 第二風格一起上。

  superset（新增 `style` 鍵，additive，既有讀 cut_loops/holes_bridged/
  components_before 不受影響）。
- 0.14.209→0.14.210、badge tests 1725→1729（+4 離線）、node 257 不變、零新增

## 5en：逐字手寫範字符合字型風格——用預覽字形非系統字型（0.14.218，純前端）

**實機回報 bug 修復**（使用者部署後實測）：抄經選篆書，逐字手寫視窗的淡色
範字顯示**楷書「觀」不是篆書**——誤導使用者照楷書寫。

### 根因

`swDrawBase`（index.html）用 `ctx.fillText(cur.char, …, "'Noto Sans TC'…")`
以**系統 sans-serif 字型**畫範字，不管字型風格選什麼都畫楷/黑體。篆/隸字形

### 做法（純前端，reuse 已渲染字形）

- 新增 `swBuildRefImg(cur)`：從**抄經預覽（#st-preview）已渲染的 SVG** 取該
  格 cellmap rect 的 bbox，clone 範字圖層（`sutra-glyph-reference` /
  `sutra-trace` / `sutra-trace-skeleton`——**排除** user 手寫/marks/cellmap），
  包成 `viewBox=cell bbox` 的新 SVG（裁到該格）、recolor 成清晰淺灰 #c8c8c8
  （原印刷層 opacity 極低、直接 clone 會隱形），載成 Image。缺字/無預覽/錯誤
  → 回 null。
- `swLoadCurrent` 每字 async 重建 `SW.refImg`（載好後 swRedraw）。
- `swDrawBase`：有 `SW.refImg` → `drawImage`（styled 範字，符合篆/隸/宋）；
  無 → fallback 原 fillText（系統字型，僅缺 styled 時用、明示不匹配篆/隸）。
- canvas 不透明白底，故範字必須畫在 canvas 上（墨之下）——用 drawImage 於
  swDrawBase 內（同步、Image 已於 swLoadCurrent 預載），而非疊層。

## 5ep：逐字手寫範字修復 v2——5en 用錯元素 id（0.14.220）

**實機回報：5en 沒生效**——篆書抄經逐字手寫範字仍是實心楷書（fillText
fallback 觸發＝swBuildRefImg 回 null）。

### 根因（元素 id 前綴弄錯）

5en 的 `swBuildRefImg` 用 `document.getElementById("st-preview")` 取抄經預覽
——但 **`st-`＝印章 stamp（st-render→stampRender）**、抄經是 **`su-`
（su-render→sutraRender、`#su-preview`）**。於是 production 抓到印章預覽（抄經
模式下無 cellmap）→ 查無 → 回 null → fallback 系統字型楷書。

**為何 5en 測試沒抓到**：5en 的 e2e 用**注入的 mock `st-preview`**（且搬到
body）、pytest 只鎖字串 wiring——**都沒對真實 sutraRender 產出的 `su-preview`
測**。教訓：JS 讀 DOM 元素的修復，務必對**真實渲染的元素**做端到端測，別用
自己捏的 mock（mock 會遷就錯誤假設而通過）。

### 修法

- `swBuildRefImg`：`getElementById("st-preview")` → **`getElementById("su-preview")`**
  （一處、一詞之差）。
- pytest 5en 斷言加鎖：swBuildRefImg 函式體須含 `su-preview`、不得含
  `st-preview`（切函式體比對，因 st-preview 是印章模式合法使用、不能全域禁）。

## 5eq：逐字手寫篆書範字太粗——只複製填實字形層、不疊粗骨架（0.14.221，純前端）

### 實機回報（承 5ep 驗收）

5ep 驗收通過——抄經選篆書、逐字手寫視窗範字已是篆書（不再楷書）。但新問題：
篆書範字**筆劃太粗、筆畫互相重疊糊成一團、與格子描紅的大小比例略偏大**。

### 根因（圖層堆疊 + 全 opacity=1）

`swBuildRefImg`（5en）一次 clone 抄經預覽的三個範字層並把 opacity 全設 1：
- `sutra-glyph-reference`：**填實**外框（fill、stroke=none），預覽 opacity 0.55
  ——即格子裡看到的細灰篆形（篆書真正的範字）。
- `sutra-trace`：楷/宋填實外框（篆書為空）。
- `sutra-trace-skeleton`：**中線骨架**，`fill=none`、stroke-width＝char_size×0.12
  （12%＝挺粗）、預覽 opacity **0.03**（隸/篆刻意調到幾乎透明的 hint）。

篆書＝skeleton 模式（sutra.py 註解 §47-76）：格子主要靠 0.55 填實層呈現、0.03
骨架幾乎看不見。但 popup 把 0.55→1（變重）、**0.03 的 12% 粗骨架也拉到 1 全顯**、
疊在填實層上 → 又粗又重疊的黑團；且骨架 round-cap 端點超出字形 bbox → 看起來
比例偏大。三個症狀同源。

### 修法（最小、純 index.html）

`swBuildRefImg` 改為**只複製填實字形層**：有 `sutra-glyph-reference`/`sutra-trace`
任一即用填實集、否則才 fallback `sutra-trace-skeleton`（罕見：無填實外框時）。
篆書於是拿到細的填實篆形＝格子描紅那個樣子；不再疊 12% 粗骨架 → 不粗、不重疊、
無 round-cap 溢出 → 比例也貼合。opacity 1 + recolor #c8c8c8 對單一填實層＝乾淨
淺灰描紅。

### 驗證（對真實渲染跑 e2e，非只靜態鎖）

- `e2e_5eq`（真瀏覽器、真 swBuildRefImg）：注入「填實 reference + 12% 粗
  skeleton 並存」的篆書情境 mock 預覽（沙箱無真篆體字型，故用 mock 逼出並存）→

  （踩點：頁面既有 #su-preview 在隱藏抄經區塊、getBBox=0；e2e 移除後在 body 建
  可見同 id host 才量得到——對映 §33 真實渲染驗接線。）

### 教訓

reuse 伺服器渲染的多圖層 SVG 當前端 styled 範字時（§32/5en），**要挑對「代表
該風格的那一層」、別無腦全 clone 並拉 opacity=1**——各層的 opacity/stroke 是為
「印刷描紅疊合」調的（填實 0.55 + 骨架 0.03），平權堆疊會把 hint 層（粗骨架）
放大成主體。篆書的代表層是填實外框、不是那條粗中線。
