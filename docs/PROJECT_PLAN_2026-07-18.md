> (a) **VISION 主線**（三維交集、個人字庫生成）——那 Line B 就該凍結，回 Phase B。

## 6. UI 質感與按鈕佈局檢視【新專章】

> 本章回應你的「讓操作介面更有質感、檢視按鈕排列及分布」。分三層：**資訊架構（模式怎麼分）→ 按鈕佈局（每個模式內怎麼排）→ 視覺質感（怎麼看起來精緻）**。每項附**原因與策略**（供 §12 憲章與未來修訂遵循）。

### 6.1 現況問題（實測 index.html）

- **14 模式扁平並列**：一排 radio，新使用者第一眼要在 14 個對等選項裡找路——認知過載。模式其實有清楚的三大類，但佈局沒表達。
- **133 個 button、74 個 onclick，缺一致語彙**：主要動作（產生／下載）、次要動作（清空／復原）、破壞性動作（刪除）在不同模式用不同樣式與位置，使用者要重新學每個模式。
- **設定面板資訊密度不均**：抄經模式一次攤開分類／經典／字型／抄寫者／文字處理／紙張方向／封面……十幾個欄位平鋪，沒有「基本 vs 進階」分層。
- **視覺質感未系統化**：inline `<style>` 僅 11 KB、無設計 token（顏色／間距／圓角／陰影散落硬寫）、無一致的 spacing scale 與 type scale。

### 6.2 資訊架構重組：14 模式分 3 群（+ 逐字手寫為互動層）

| 群組 | 模式 | 共同語意 |
|---|---|---|
| **A. 書寫練習** | 單字・字帖・筆記・信紙・稿紙 | 「把字寫好」——描紅、格線、練習頁 |
| **B. 製造與切割** | 塗鴉・布章・印章・鏤空字 | 「把字變成可製造的線稿」——CNC／雷雕／噴漆／裁切 |
| **C. 藝術與創作** | 抄經・文字雲・曼陀羅・禪繞字 | 「把字變成作品」——排版、圖形、療癒創作 |

**原因**：三群對應三種**使用者意圖**（練字／製造／創作），不是隨意分類——分群後首屏從「14 選 1」變「先選意圖、再選模式」，認知負荷從 O(14) 降到 O(3)+O(≤5)。**策略**：用**分群標籤頁（tab）或分段卡片**取代扁平 radio；預設落在最常用群（用 §Stage 0 儀表數據決定，不用猜）。**這也是 §7 分段載入的天然邊界**——切一個群就是一個 lazy chunk。

### 6.3 按鈕佈局原則（統一語彙）

建立**四級按鈕語彙**，全模式一致：

1. **主要動作（Primary）**：每個模式最多一個，實心強調色，固定在**設定面板底部右側**（如「產生預覽／下載 PDF」）。
2. **次要動作（Secondary）**：描邊或淺底（如「下載 SVG／G-code」），排在主要動作左側同一行。
3. **輔助／可逆（Tertiary）**：純文字或圖示鈕（清空／復原／匯入），放工具列或就近元素旁。
4. **破壞性（Destructive）**：紅色系＋需二次確認（刪除罕用字、清空全部）。

**原因**：現在使用者要為每個模式重新學按鈕在哪、哪個是主動作；統一語彙後**肌肉記憶可跨模式遷移**。**策略**：抽一組共用 CSS class（`.btn-primary/.btn-secondary/.btn-ghost/.btn-danger`）＋固定的 action-bar 版位；逐字手寫彈窗那種多鈕面板（復原／清空／播放／示範／上下字／略過／送出）依此四級重排——目前它把 7 個鈕平鋪，應分成「畫布工具列（可逆）」＋「導覽（上下字）」＋「主要（送出）」三區。

### 6.4 視覺質感升級（設計 token 化）

- **建一組 design token**（CSS 變數）：`--space-{1..8}`（8 px 基準間距階）、`--radius-{sm,md,lg}`、`--shadow-{1,2}`、`--font-size-{xs..xl}`、語意色（`--color-primary/surface/border/muted/danger`）。
- **一致的卡片與留白**：設定面板、預覽區、模式卡用同一組 surface/border/radius/shadow；拉開留白（現在密度過高）。
- **狀態回饋**：載入中（骨架屏或 spinner）、成功（綠勾）、錯誤（紅字＋可重試）統一元件——尤其配合 §7 分段載入時的「載入進度」。
- **深色模式（可選遠期）**：token 化後幾乎免費。

**原因**：質感 = 一致性 × 留白 × 回饋，不是加裝飾。token 化讓「改一次、全站一致」，也是未來維護的槓桿。**策略**：token 先行（半 session），再逐模式套用；**先不換框架**（不引入 Tailwind/組件庫），用原生 CSS 變數即可達到質感，避免 §7 的肥大問題雪上加霜。

### 6.5 UI 改版的紅線

**漸進增強、不破壞**（§12-P12）：每次只重排一個群／一個模式的 UI，保留原功能與 URL 行為；改完跑該模式 Playwright 冒煙＋截圖對照（§8.15）。**絕不**一次全站改版——那會同時引入視覺回歸與功能回歸，難分病灶（§28 拆 commit 精神）。

## 7. 前端效能與架構重構【新專章】

> 回應你的「避免程式在網頁執行負擔太重導致系統崩潰、研究分段載入或精簡程式」。核心結論：**問題不在演算法，在「一次載入全部」**——453 KB 單檔＋5 支 eager 外部庫，不管使用者只用哪一個模式。

### 7.1 診斷（實測數據）

| 項目 | 現況 | 問題 |
|---|---|---|
| `index.html` | 453 KB 單檔 | 首屏要解析整份；改動風險半徑＝全檔 |
| inline `<script>` | **295 KB／65%／235 functions** 一整塊 | 14 模式邏輯全 eager；瀏覽器一次編譯全部 |
| 外部庫（eager） | hanzi-writer、pinyin-pro、js-yaml、doodle_engine.js、zentangle.js | 用單字模式也載了 zentangle／OpenCV 級資源 |
| build system | 無 | 無 tree-shaking／無 code splitting／無 minify |
| 崩潰風險點 | 塗鴉（OpenCV/canvas）、抄經（260 字位渲染）、文字雲／曼陀羅（大量 SVG 節點） | 重模式在低階裝置累積記憶體 |

### 7.2 分段載入策略（漸進式，不引入重型 build）

**核心手法＝按「模式群」動態載入（route-level code splitting），用原生 ES module `import()`，不必 webpack。**

1. **拆檔**：把 295 KB inline script 依 §6.2 三群拆成 `core.js`（共用：IR 呼叫、預覽框架、按鈕語彙）＋ `group-write.js`／`group-make.js`／`group-art.js`（各群模式邏輯）。首屏只載 `core.js`。
2. **按需動態 import**：使用者點某群 tab → `await import('./group-make.js')` 才載該群；載入時顯示**進度／骨架屏**（呼應你的「呈現進度表」在 UI 層的一面）。
3. **重型外部庫 lazy**：hanzi-writer 只在「✎示範」時載；OpenCV 只在塗鴉模式載；zentangle.js 只在禪繞模式載；pinyin-pro／js-yaml 按需。用 `<script>` 動態插入或動態 import，**首屏 5 支 eager → 0 支**。
4. **Web Worker 卸載重算**：塗鴉 OpenCV、抄經多字渲染移到 worker（doodle_worker.js 已有先例），主執行緒不凍、不崩。
5. **精簡**：移除死碼、重複工具函式抽共用（235 functions 裡必有重複）；靜態資源加 `?v=` cache-bust（已有慣例）＋長快取。

### 7.3 崩潰防護（防「系統崩潰」）

- **記憶體釋放**：切模式時銷毀上一模式的大物件（canvas context、SVG 節點、OpenCV Mat）；目前很可能累積不釋放。
- **上限保護**：文字雲／曼陀羅／抄經對「字數／節點數」設軟上限＋警告（超過先提示，別直接卡死）。
- **錯誤邊界**：每個模式包一層 try／catch＋友善錯誤 UI（可重試），單一模式炸掉不拖垮整頁。
- **載入失敗降級**：CDN 庫載入失敗時給明確提示與 fallback（呼應 §5.26 降級階梯誠實）。

### 7.4 為什麼這樣做（原因與策略）

- **原因**：效能問題的 80% 來自「全載」而非「算得慢」——量測（§O 先量再改）顯示是 payload／解析／記憶體，不是演算法。故解法是**切載入邊界**，不是重寫演算法。
- **策略＝漸進、不換框架**：原生 ES module 動態 import 就能拿到 90% 的分段載入紅利，**避免引入 webpack/Vite 反而增加建置複雜度與另一種肥大**（§12-P10）。這也守住「純 index.html 改動免大重構」的既有節奏。
- **策略＝一次搬一個模式**：對應 §6.5 與 §28（拆 commit）——每搬一個模式 chunk，跑該模式 Playwright 冒煙＋比對輸出逐位元不變，session-sized、可中斷、易回溯。

### 7.5 效能目標（可量測驗收）

| 指標 | 現況（估） | 目標 |
|---|---|---|
| 首屏 JS payload | ~350 KB+（含 5 庫） | < 80 KB（只 core） |
| 首屏 eager 外部庫 | 5 支 | 0 支 |
| 切模式峰值記憶體 | 累積不釋放 | 切模式後回落 |
| 重模式主執行緒阻塞 | 有（塗鴉/抄經） | 移 worker、不阻塞 |
