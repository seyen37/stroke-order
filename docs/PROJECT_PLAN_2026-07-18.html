戰略張力：存在理由分叉

the honest fork

7/05 推薦「凍結 Line B、回主線 Phase B」。但這 13 天你主動深化 Line B（抄經／切割／逐字手寫），每弧品質都高。這逼出一個必須顯性拍板的問題——這次修訂最重要的產出。

路徑 (a)

VISION 主線

三維交集、個人字庫生成。「寫 1/5 的字，留下全部字跡」。
→ 那 Line B 該凍結，回 Phase B 組件切割。

路徑 (b)

中文字創作／製造工具站

14 模式一站式：練字／字帖／抄經／切割／印章。
→ 那 Line B 是主體，該投資它的 UI 質感與效能（＝你這次的請求）。

本檔不替你決定，但把它從「隱性偏離」變「顯性選擇」。妙處：無論 (a)/(b)，「前端不崩、UI 好用」都是共同地基——所以先做它是零後悔，且過程中的儀表數據會讓 (a)/(b) 在 Stage 2 用數據拍。

前端效能與分段載入

performance

問題不在演算法，在「一次載入全部」。解法＝切載入邊界（原生 ES module 動態 import()），不引入重型 build。

首屏 JS payload~350 KB+ → < 80 KB
只載 core.js；三群按需 import
首屏 eager 外部庫5 支 → 0 支
hanzi-writer 只在「示範」載・OpenCV 只在塗鴉載・zentangle 只在禪繞載
切模式峰值記憶體累積不釋放 → 切換後回落
切模式銷毀上一模式的 canvas／SVG 節點／OpenCV Mat
重模式主執行緒阻塞 → 移 Worker
塗鴉 OpenCV／抄經多字渲染卸到 worker，主緒不凍不崩
① 拆檔

295 KB → core.js ＋ group-write／make／art.js。首屏只載 core。

② 按需 import

點群 tab 才 await import()，載入時顯示進度／骨架屏。

③ 崩潰防護

記憶體釋放＋字數上限警告＋每模式錯誤邊界＋CDN 失敗降級。

推薦決定

recommendation
★ Option A：前端健康化優先

三個理由：①直接解你當下真實痛點（效能/崩潰/UI，動機最強不易懸置）；②零後悔投資——無論最後選 (a) 或 (b)，「前端不崩、UI 好用」都是共同地基，且過程中儀表數據讓 (a)/(b) 用數據拍；③配合已驗證的工作模式——13 天證明你在「有實機回饋、單 session 可閉合」的前端工作最有續航力。

QODA sign-off 範圍 ＝ Stage 0（舊債＋儀表）＋ Stage 1（第一個模式群分段載入 PoC ＋ UI mockup 對焦），合計 3–4 sessions。存在理由 (a)/(b) 與全量在 Stage 2 用數據拍——你現在不必承諾 (a)/(b)。

進度表 · 執行藍圖

roadmap

每步＝1 session 可閉合，標驗收與 kill。順序即優先序。

Stage 0

閉合與地基 · 1–2 sessions

  • root 樣本歸檔
  • 最小儀表：mode×日期 計數＋/api/stats（供 (a)/(b) 拍板）
  • Line B 凍結敘事對焦（暫緩結論等 Stage 2）
Stage 1

前端健康化 PoC · 2–3 sessions

  • 抽 design token＋四級按鈕語彙，先套 1 模式
  • 三群資訊架構 mockup 對焦
  • 分段載入 PoC：拆 1 群成 lazy chunk＋重庫按需＋載入進度｜驗收：該群冒煙綠、輸出逐位元不變｜kill：收益<20%
Stage 2

Checkpoint（QODA）· 半 session

  • 用儀表數據＋PoC 成效，拍：①存在理由 (a)/(b)；②前端全量 or 轉主線。寫決策日誌。
Stage 3

前端健康化全量 · 3–5 sessions，一次一群

  • 三群全拆 lazy chunk＋全模式套 token/按鈕語彙＋崩潰防護
  • 驗收：首屏 JS <80 KB、eager 庫 0 支、記憶體回落、14 模式冒煙全綠
Stage 4

分叉（依 Stage 2）· 依選擇

  • 選 (a)：Phase B spike 命中率 → Phase B/C 全量
  • 選 (b)：蓄水四缺口＋教育現場試點（你的天然通路）
Stage 5

遠期觸發（只列條件，不排程）

  • Phase D（≥5000 字樣本）／tinyhanzi／KAGE 整合／學術發表／深色模式

策略原則憲章

charter · P1–P12

承 7/05 的 P1–P9（不變），本次新增三條對應 UI／效能兩軸——未來修訂遵循。

P10 前端健康＝零後悔，但不換框架

分段載入／崩潰防護優先於加功能；原生 ES module import 拿 90% 紅利，避免重型 build 造成另一種肥大。先量 payload／記憶體／阻塞再改。

P11 UI 一致性 > 局部美化

先立資訊架構（意圖分群）＋按鈕四級語彙＋design token，再談個別視覺。一致性讓肌肉記憶跨模式遷移、改一次全站一致。

P12 漸進增強、不破壞

UI／前端重構一次只動一模式／一群，保留原功能與行為，改完跑冒煙＋截圖對照。絕不一次全站改版（回歸難分病灶）。
